# Evaluation — driving v0.21 with released Spark v0.20.0 as the operator

> Development-only record. Not shipped. This is the ledger of a dogfood run in
> which milestone #18 (v0.21 — Governance as schema) was driven from its live
> state to release readiness using the **published** Spark v0.20.0 artifact as
> the operator, to find out where that release actually carries a delivery
> workflow and where the agent is still acting as an implicit control plane.
>
> Every cycle records: what Spark selected, what it routed, what it determined
> mechanically, what reasoning the agent still had to supply, which human
> decisions were genuinely required, and every defect found — including the
> ones in the agent's own work, which are the majority.

`~/.claude/plugins/cache/spark/spark/0.20.0`, `gitCommitSha fd407c72`, which is
exactly the `v0.20.0` tag and (at run start) `origin/master`. `which spark`

### Milestone-metadata contradiction — needs a human decision

Not a Spark defect: Spark is right about its inputs. The inputs disagree with
each other. Gate #478 carries two authorities that cannot both hold:

- **The sub-issue order** puts #483 last (position 5 of 5). Following it,
  selection goes #471 → #472 → #473 → #483, because each closure unblocks the
  next and #483 loses every P1 tie on order.
- **The self-hosting rule** in the same gate says: "Once #483 has landed, every
  remaining issue in this milestone must carry a satisfied `docs-impact`
  disposition — #471, #472, #473, and this gate included."

Under the gate's own order, #471, #472, and #473 are all **closed** by the time
#483 lands, and #483's non-goals explicitly exclude "retrofitting dispositions
onto already-closed issues". So the rule as written can only ever apply to #478.
The gate names three issues it structurally cannot cover.

**Why this does not block cycle 2.** #471 is required under either resolution —
#483's own acceptance criteria demand its label family be "provisioned and
validated through #471's generic path", so #471 precedes #483 functionally even
with no native edge. Work proceeds. The decision becomes load-bearing before
#472 closes, which is why it is raised now rather than at the endgame.

**The decision is the human's** — it is milestone sequencing intent, and either
resolution is a remote metadata mutation:

- (a) reorder the gate's sub-issues so #483 lands second, making the
  self-hosting rule literally true; or
- (b) amend the gate to scope self-hosting to whatever is still open when #483
  lands (in practice #478 alone), and record #471/#472/#473 as bootstrap
  exceptions alongside #470.

   having just fixed the first one.

### Repair cycle 3 — #512, a failed evidence layer is not an empty one

Operator selected #512 (P1, order 8 of 13, 3 candidates excluded as blocked).
Accepted without substitution.

`docs-impact --branch` read the linked-PR lookup as
`prs="$(di_linked_prs ...)" || prs=""`, which makes a failed query and a
successful query returning nothing the same value. The branch-only evidence was
then graded as complete: `docs-impact:none` PASSed with exit 0 while the earlier
merged PR that contradicted it was silently absent. `validate` runs this verb, so
a transient GraphQL error let the lifecycle proceed.

The fix is that each evidence layer reports which of its two outcomes happened,
and only one of them is an answer:

| Layer | Answered | Failed |
| --- | --- | --- |
| linked-PR lookup | no PR linked yet — the branch diff is the whole set, and is graded | NOT ASSESSED, layer `linked-pr-lookup` |
| a linked PR's files | the paths join the union | NOT ASSESSED, layer `pr-files` |
| repository identity | owner/name resolved | NOT ASSESSED, layer `repo-identity` |

Keeping the *empty success* gradeable is as important as failing the failure: a
genuinely first branch has complete evidence, and turning that into NOT ASSESSED
would make the verb unusable before any PR exists. The suite asserts both
directions.

**Measured discrimination:** restoring the branch-mode conflation turns 8 of the
suite's 21 assertions red — including the reported symptom exactly, `PASS` with
exit 0 where a FAIL was due. Restoring the default mode's half turns 2 red.

Two design notes worth recording, because both were judgment rather than
mechanics:

- The default mode was, as the issue said, *safe by accident* — the empty value
  fell into a NOT ASSESSED return. But its message asserted a fact the failed
  query had not established: "issue #N has no merged or open implementation PR".
  A correct verdict with a false reason sends an author to open a PR that already
  exists, so the two are now separate findings with separate layer names.
- `ev_note` became write-never once every partial-evidence path reports and
  stops. Deleting it would have removed a documented `--tsv` record type; instead
  it now carries the **layer name in its own column**, so a consumer branches on
  which layer failed rather than parsing prose. A machine-readable row was one of
  the issue's own acceptance criteria.

**Self-review found a defect the whole 21-assertion suite could not see.** Every
assertion read `--tsv`; the human renderer is a separate path, and the first cut
printed the finding twice there — once as a note, once as the verdict — reading
as two problems. Five human-mode assertions were added, and re-introducing the
duplication turns one red. The lesson is the same one this milestone keeps
teaching in new clothes: a suite proves the surface it drives, and a surface no
assertion drives is unproven no matter how many assertions there are.

**#526 — the bash guard blocks commands that only quote a forbidden pattern.**
Found with the *released* v0.20.0 hook, not the code under test. It refused two
calls in a minute: a test fixture publishing a seed commit to a bare repo created
two lines earlier under `$TMPDIR`, and then — the sharp one — a `python3` patch
script that ran no git command at all and whose only sin was containing the
string it was about to delete from a test file. The guard refused the edit that
would have satisfied it.

Filed at P2 with no milestone. Worth stating plainly in Spark's own terms: the
guard should stay strict, and a false negative here would be far worse than a
false positive. The defect is not what it forbids but that a text matcher makes
its scope unpredictable, and the natural response to an unexplained refusal is to
reword the command until it passes — the exact habit a guard must not teach. The
filed criteria therefore require the real cases to be proven still blocked
alongside any fix.

The fixture was changed to write `refs/remotes/origin/master` directly instead,
which is faster and does not read as publishing to a trunk. That is the better
fixture regardless of the guard.
