# Evaluation — driving v0.21 with released Spark v0.20.0 as the operator

> Development-only record. Not shipped. This is the ledger of a dogfood run in
> which milestone #18 (v0.21 — Governance as schema) was driven from its live
> state to release readiness using the **published** Spark v0.20.0 artifact as
> the operator, to find out where that release actually carries a delivery
> workflow and where the agent is still acting as an implicit control plane.
>
> Every cycle records: what Spark selected, what it routed, what it determined
> mechanically, what reasoning the agent still had to supply, which human
> decisions were genuinely required, and every defect found — including the
> ones in the agent's own work, which are the majority.

`~/.claude/plugins/cache/spark/spark/0.20.0`, `gitCommitSha fd407c72`, which is

### Milestone-metadata contradiction — needs a human decision

Not a Spark defect: Spark is right about its inputs. The inputs disagree with
each other. Gate #478 carries two authorities that cannot both hold:

- **The sub-issue order** puts #483 last (position 5 of 5). Following it,
  selection goes #471 → #472 → #473 → #483, because each closure unblocks the
  next and #483 loses every P1 tie on order.
- **The self-hosting rule** in the same gate says: "Once #483 has landed, every
  remaining issue in this milestone must carry a satisfied `docs-impact`
  disposition — #471, #472, #473, and this gate included."

Under the gate's own order, #471, #472, and #473 are all **closed** by the time
#483 lands, and #483's non-goals explicitly exclude "retrofitting dispositions
onto already-closed issues". So the rule as written can only ever apply to #478.
The gate names three issues it structurally cannot cover.

**Why this does not block cycle 2.** #471 is required under either resolution —
#483's own acceptance criteria demand its label family be "provisioned and
validated through #471's generic path", so #471 precedes #483 functionally even
with no native edge. Work proceeds. The decision becomes load-bearing before
#472 closes, which is why it is raised now rather than at the endgame.

**The decision is the human's** — it is milestone sequencing intent, and either
resolution is a remote metadata mutation:

- (a) reorder the gate's sub-issues so #483 lands second, making the
  self-hosting rule literally true; or
- (b) amend the gate to scope self-hosting to whatever is still open when #483
  lands (in practice #478 alone), and record #471/#472/#473 as bootstrap
  exceptions alongside #470.

### Repair cycle 3 — #512, a failed evidence layer is not an empty one

Operator selected #512 (P1, order 8 of 13, 3 candidates excluded as blocked).
Accepted without substitution.

`docs-impact --branch` read the linked-PR lookup as
`prs="$(di_linked_prs ...)" || prs=""`, which makes a failed query and a
successful query returning nothing the same value. The branch-only evidence was
then graded as complete: `docs-impact:none` PASSed with exit 0 while the earlier
merged PR that contradicted it was silently absent. `validate` runs this verb, so
a transient GraphQL error let the lifecycle proceed.

The fix is that each evidence layer reports which of its two outcomes happened,
and only one of them is an answer:

| Layer | Answered | Failed |
| --- | --- | --- |
| linked-PR lookup | no PR linked yet — the branch diff is the whole set, and is graded | NOT ASSESSED, layer `linked-pr-lookup` |
| a linked PR's files | the paths join the union | NOT ASSESSED, layer `pr-files` |
| repository identity | owner/name resolved | NOT ASSESSED, layer `repo-identity` |

Keeping the *empty success* gradeable is as important as failing the failure: a
genuinely first branch has complete evidence, and turning that into NOT ASSESSED
would make the verb unusable before any PR exists. The suite asserts both
directions.

**Measured discrimination:** restoring the branch-mode conflation turns 8 of the
suite's 21 assertions red — including the reported symptom exactly, `PASS` with
exit 0 where a FAIL was due. Restoring the default mode's half turns 2 red.

Two design notes worth recording, because both were judgment rather than
mechanics:

- The default mode was, as the issue said, *safe by accident* — the empty value
  fell into a NOT ASSESSED return. But its message asserted a fact the failed
  query had not established: "issue #N has no merged or open implementation PR".
  A correct verdict with a false reason sends an author to open a PR that already
  exists, so the two are now separate findings with separate layer names.
- `ev_note` became write-never once every partial-evidence path reports and
  stops. Deleting it would have removed a documented `--tsv` record type; instead
  it now carries the **layer name in its own column**, so a consumer branches on
  which layer failed rather than parsing prose. A machine-readable row was one of
  the issue's own acceptance criteria.

**Self-review found a defect the whole 21-assertion suite could not see.** Every
assertion read `--tsv`; the human renderer is a separate path, and the first cut
printed the finding twice there — once as a note, once as the verdict — reading
as two problems. Five human-mode assertions were added, and re-introducing the
duplication turns one red. The lesson is the same one this milestone keeps
teaching in new clothes: a suite proves the surface it drives, and a surface no
assertion drives is unproven no matter how many assertions there are.

**#526 — the bash guard blocks commands that only quote a forbidden pattern.**
Found with the *released* v0.20.0 hook, not the code under test. It refused two
calls in a minute: a test fixture publishing a seed commit to a bare repo created
two lines earlier under `$TMPDIR`, and then — the sharp one — a `python3` patch
script that ran no git command at all and whose only sin was containing the
string it was about to delete from a test file. The guard refused the edit that
would have satisfied it.

Filed at P2 with no milestone. Worth stating plainly in Spark's own terms: the
guard should stay strict, and a false negative here would be far worse than a
false positive. The defect is not what it forbids but that a text matcher makes
its scope unpredictable, and the natural response to an unexplained refusal is to
reword the command until it passes — the exact habit a guard must not teach. The
filed criteria therefore require the real cases to be proven still blocked
alongside any fix.

The fixture was changed to write `refs/remotes/origin/master` directly instead,
which is faster and does not read as publishing to a trunk. That is the better
fixture regardless of the guard.

### Repair cycle 5 — #515, one rule for "#N"

Operator selected #515 (P1, order 9 of 13, 2 candidates excluded as blocked).
Accepted without substitution.

obviously correct in isolation, and disagreed only on inputs nobody had tried.

### Repair cycle 6 — #517, a verification gate that covered a subset

Operator selected #517 (P1, order 10 of 13, 2 candidates excluded as blocked).
Accepted without substitution.

`plan verify` read **title and labels**. Nothing else. So a slate could declare a
milestone, a parent/child hierarchy, a hard dependency and an explicit delivery
order, have every one of them absent or wrong on GitHub, and still be certified
`PASS — GitHub matches the artifact`. The milestone field was read from the
artifact and then discarded, and `plan_live_rows` skipped `body-file` entirely,
so an applied body update was indistinguishable from one that never ran.

This is the largest repair of the run: six surfaces added — milestone existence
and description, created-issue milestone assignment, created-issue body, update
body, hierarchy, dependencies, and order.

**Measured discrimination: 42 of the suite's 48 assertions turn red** when the
coverage is reverted, and the last two reproduce the report verbatim.

Three design decisions worth recording, because each could have produced a check
that looks right and is useless:

- **Order is compared as *relative* placement**, because that is how it is
  applied — the declared children are placed one after another. Comparing
  absolute indices would report drift for any parent that also holds a sub-issue
  the artifact never mentioned, which is the normal case. The fixture includes
  exactly such an extra sub-issue so that the looser rule is *proven*, not just
  intended.
- **Bodies are normalised** for line endings and trailing blank lines before
  comparison. GitHub returns CRLF for bodies submitted with LF, so the naive
  comparison reports every correct body as drifted — and a check that always
  fails gets switched off, which is worse than no check.
- **The three scalar facts are read in one call.** Adding milestone and body as
  separate `gh issue view` invocations would have doubled the call count and
  allowed the facts to be mutually inconsistent; one `--json title,labels,milestone`
  read keeps the count where it was and the facts consistent.

**The fixture could not fail on its first attempt, and the reason is worth
stating.** The wrong-order scenario passed, because the artifact ordered a single
child — and the relative order of one element is trivially correct. No amount of
stub trickery could have made that assertion fail. A second ordered child was
added, and the swap then registers. This is the fifth time in this milestone that
an assertion was structurally incapable of failing; the tell each time was a
fixture chosen for the *smallest thing that exercises the code path* rather than
the smallest thing that can distinguish right from wrong.

### Repair cycle 7 — #518, order is a fact about siblings

Operator selected #518 (P1, order 11 of 13, 2 candidates excluded as blocked).
Accepted without substitution.

Placement used **one global `prev`**, so with two independent hierarchies the
second parent's first child was handed an `after_id` belonging to a child of the
*first* parent — a placement GitHub cannot make. A valid multi-parent plan
therefore created and wired its remote state, ordered the first group, and failed
part-way through the second.

Positions were also unique **globally**, so two independent gates could not each
declare a first child. An artifact format built to carry several milestones and
hierarchies could not express their order.

Both halves have the same cause: order was treated as a property of the artifact
when it is a property of a **parent's sibling set**. GitHub holds it nowhere else.

Two judgment calls worth recording:

- **"No parent" became its own scope rather than an exemption.** Scoping
  positions per parent made the existing "two issues cannot share a position"
  case pass, because neither ref was attached to anything. The tempting reading
  was that unattached records are unplaceable anyway so a duplicate does not
  matter — but it stops being visible the moment the parents are added, and the
  artifact was wrong when it was written. Unattached refs are now one scope
  together.
- **A child under two parents is refused only when something orders it.** The
  ambiguity is about ordering, not hierarchy, and refusing the hierarchy would
  have been a wider change than the defect justifies. The suite asserts both
  directions so the narrowness is deliberate rather than accidental.

**Measured discrimination:** of the suite's 20 assertions, restoring the global
`prev` turns **2** red — reporting the leak verbatim, *"B under P2 has after_id
A2, which is not its sibling"* — and restoring the global position check turns
**5**, starting with the valid two-gate artifact being refused.

The `prev` half turning only 2 red is worth noting rather than glossing: the
defect has a narrow observable surface (one field on one emitted row) even though
its consequence is a half-applied remote mutation. A count of reds measures how
many assertions touch a defect, not how much it matters.

### Repair cycle 9 — #520, a warning is not a gate

Operator selected #520 (P1, order 12 of 13, 1 candidate excluded as blocked).

### A finding I did NOT act on, because it is the human's call

Re-auditing C1 exposed something real and then tempted me into the wrong fix.

A repository that Spark has just correctly set up **FAILs its own
`spark governance validate`**. The cause: `.github/ISSUE_TEMPLATE` and
`.github/pull_request_template.md` are declared `human-provisions`, so Spark
deliberately does not create them, and `gov_file_rows` grades an absent
human-owned surface `!` — "needs human judgment" — which the verdict logic reads
as FAIL.

My first move was to change `!` to `+` ("missing/safe"), on the reasoning that an
absent template is *missing* with an unambiguous remedy, and that a brand-new
repo reporting FAIL teaches an operator that FAIL is the normal state. The change
was written, and it worked: a fresh repo then reported NOT ASSESSED, which is
honest about the unread GitHub surfaces.

**Two existing assertions failed** — `"a missing human-owned surface is judgment,
not a create"`, in two suites. The behaviour is deliberate, with a stated
rationale: `+` carries the implication *Spark can fix this*, which is false for a
surface only a human can provision.

So this is a genuine disagreement about product semantics, not a defect, and it
belongs to the human. **I reverted the change.** The tension is real either way:

- as `!`, every correctly onboarded repository fails its own governance on day
  one, and the operator learns to discount FAIL;
- as `+`, the row implies Spark could provision something it cannot.

A third option neither reading covers: a distinct row for "declared, absent, and
only a human can supply it" — expected-absent rather than either missing or
invalid. That is a vocabulary change, and the vocabulary is the schema's.

Filed as **#535** at P3 with no milestone, with all four options written out and
the reverted patch described. It is a decision, so it is stated as one.

**My C1 assertion was also wrong, and wrong in the dangerous direction.** It
asserted that a fresh repo must pass `governance validate` — which is not what
the criterion says. The criterion is that Spark provisions *its* surface
deterministically, and that is proven by two fresh repos resolving an identical
model. An audit assertion that overreaches its criterion is how tested,
deliberate behaviour gets changed to make an audit green.

text reconciling the two. The direction is not to change `!` to `+` to make the
report green; it is to narrow the contract so it distinguishes Spark-provisioned
governance from human-provisioned prerequisites, and to keep missing human-owned
surfaces explicit.

All three were admitted to the milestone and the gate; #483 was made natively
blocked by #530 and #524; #473 was reopened for its truth correction. #508, #526
and #539 stay out — none was shown to falsify a criterion.

**A metadata contradiction surfaced during the reconciliation and was fixed
rather than tolerated.** Adding #530 and #524 put them *last* in the gate's
sub-issue order while #483 — which they block — sat second. The blocked-by graph
would have kept selection correct, but the preferred order would have said the
opposite of the prerequisite graph: the same drift the earlier reconciliation
existed to remove. Both were repositioned after #470 before any work started, and
the operator then read *"order 2 of 19"*.

### Repair cycle 16 — #530, "all" is not "the first fifty"

Operator selected #530 (P2, order 2 of 19, 1 candidate excluded as blocked — #483,
which it blocks). Accepted without substitution.

The connection is now read page by page until `hasNextPage` is false. Three
properties had to survive, and each is asserted:

| Property | Why it is fragile |
| --- | --- |
| a **continuation** page failure is NOT ASSESSED at `linked-pr-lookup` | the first page succeeded, so nothing looks wrong — grading page one is the partial-set failure #512 fixed, relocated one layer down |
| a successful **empty** connection stays distinct from a failed lookup | the header line is what carries that distinction now, so the stub had to learn to emit it |
| `hasNextPage` true with **no cursor** is refused | continuing from the start would loop forever, and stopping silently would truncate |

**Measured discrimination: 11 of the suite's 44 assertions turn red** against the
pre-fix implementation, restored byte-exact rather than approximated. The decisive
group reproduces #530's own scenario: with 51 linked references and the only
governed documentation on PR 151, the old code returns **PASS / exit 0** where
FAIL is required.

Two of the 11 are honestly not the pagination defect — the stub now speaks the
paginated protocol, so the old code misreads the header line as a PR number. That
is unavoidable when the query shape changes, and saying which reds are decisive
matters more than the total.

**The fixture failed to discriminate on its first attempt, for a reason worth
keeping.** Its `di_pr_paths` stub returned the governed path for any PR number it
did not recognise. Measuring the old implementation then "passed": it read the
page header as a node number, asked for that bogus PR's files, and got the
governed document back — so the verdict was right *by accident* and the assertion
could not fail. A fixture whose default answer is the interesting one cannot
discriminate. Dispatch is now on the extracted PR number, and an undefined number
returns nothing.

### Repair cycle 17 — #524, a generated release PR is not implementation evidence

Operator selected #524 (P2, order 3 of 19, 1 candidate excluded as blocked — #483,
which it blocks). Accepted without substitution.

#483 defines an *"implementation-evidence set"*: *"the closing **implementation**
PR"*, *"multiple explicitly linked **implementation** PRs"*. GitHub reports the
Release Please PR as a closing reference for every issue in the release, because
its generated body repeats each `Closes #NNN` — so `#506 chore: release spark
v0.21.0` was returned as evidence for #483 and #470 alike, and graded as though a
human had written it.

**The dismissal I had used was the interesting part of this cycle.** I argued #506
touches no governed path, so the verdict is unaffected. That is true and it is a
different claim: it establishes that *today's data* does not bite, and says nothing
about whether the implementation satisfies the contract. Two claims run together.

**The signal is durable configuration, not a title match.** Release Please opens
its PR from `<branch-prefix>--branches--<base>`, and `branch-prefix` is a key in
`release-please-config.json`. A title pattern would be wrong twice over:
`group-pull-request-title-pattern` is free text a human can edit, and an
implementation PR may mention a release in its own title. Where release automation
is not configured, nothing is excluded and behaviour is exactly as before.

Two properties the fix had to carry, both asserted:

- **the exclusion is visible** — one nobody can see is indistinguishable from a PR
  that was never linked, so `evidence-excluded release-automation 506` is a row of
  its own;
- **every reference excluded is NOT ASSESSED** — that is not "no PR is linked
  yet", which is a complete answer graded on the branch, but "no implementation
  evidence could be read", which is never a pass.

**Measured discrimination: 10 of the suite's 60 assertions turn red** without the
exclusion. The fixture is the one arrangement that can discriminate: an
implementation PR carrying code only, and a release PR carrying a governed release
document, with `docs-impact:none` declared — so including it flips PASS to FAIL.

**Two defects in my own fix, both found by probing rather than by reading it.**

`local root="$1" cfg="$root/release-please-config.json"` does not dependably see
`root` within the same statement, and under `set -u` it failed loudly — so the
prefix came back empty and nothing was excluded. It surfaced only because I ran a
probe against live GitHub instead of trusting the suite, which passed throughout:
the fixtures set the config themselves and never exercised that path.

Then flattening the implementation list to spaces — needed to render the exclusion
— left `ev_desc`'s `awk` reading a single record, so the report named `PR(s) #507`
where the union genuinely contained #507 and #528. **The evidence was right and its
description was not**, which is a verdict nobody can audit from its own output. The
first assertion written for it used `--branch` and passed both ways, because branch
mode appends per iteration; only the default mode reads the list through that awk.
Moved, and it now turns red.

### Repair cycle 18 — #483 re-audited, with pagination proven specifically

Operator selected #483 (P1, order 4 of 19) once #530 and #524 closed. Accepted
without substitution.

**Result: 53 checks pass, 0 fail, 1 NOT MECHANICALLY VERIFIABLE** — unchanged:
"`validate` runs the check on the branch" is a skill contract, not a code path.

The requirement was to prove **pagination specifically, not iteration over two
returned nodes**. Those look identical when one page comes back, so the audit
drives a genuine two-page connection: 51 references, PRs 201–250 on page one
carrying code only, and PR 251 alone on page two carrying the governed reference
document, with `docs-impact:none` declared. A single-page reader never sees 251,
grades code only, and PASSes — so the assertion can only be satisfied by a reader
that asked for the second page.

| Re-checked | Result |
| --- | --- |
| the two-page aggregate | FAIL, with **both** a page-one and the page-two PR named |
| a failed continuation page | NOT ASSESSED at `linked-pr-lookup`, partial set never graded |
| release automation linked alongside an implementation PR | excluded and **visibly** so; the implementation PR still counts |
| only release automation linked | NOT ASSESSED, never PASS |

**Discrimination, measured per repair:** reverting #524's exclusion turns 4 of the
53 red; reverting #530's pagination turns **17**.

**Four faults in the audit harness, and every one of them was silent.**

- `crit` takes two arguments and the new sections passed one, so `$2` was unbound
  under `set -u`.
- `eq`, `has` and `hasnt` were never defined in this script — they came from a
  sibling audit. They failed as *"command not found"*, which prints no PASS and no
  FAIL, so **the whole section contributed nothing to the totals while appearing
  to run**. A missing assertion helper is an assertion that cannot fail, and it is
  the most invisible form of it yet in this run.
- the pre-existing stub still emitted bare PR numbers, so the paginated reader saw
  a malformed header and reported a failed lookup — a fixture fault reading exactly
  like a defect.
- the file stub matched `$args` with a pattern ending at `/files`, which never
  fires because `--jq` follows on the command line. Every file list came back
  empty, so the fixture could not discriminate. **The same mistake the committed
  suite's stub had already taught**, repeated three cycles later in a different
  file — which is the argument for extracting the PR number rather than
  pattern-matching a command line.

**The truth check caught its own model being wrong, which is the best thing that
happened this cycle.** Adding #483's second re-audit row made it report *"the
release record's repairs table names an issue twice"* — because #546's vocabulary
had asserted repair issues and repair cycles were 1:1 *"by definition"*. That was
true when written and false as soon as an issue was reopened twice.

The fix is the model, not the symptom: cycles are derived from the cycle headings
and the repairs table's row count, issues from the **distinct** issue numbers in
that table, and each is compared against the claim that names it. An issue may
now legitimately appear twice; a row with no cycle behind it, or a tally that
disagrees with the distinct count, still fails. Eighteen cycles over seventeen
issues.

Writing "by definition" was the tell. A definition cannot make a fact about
future work true, and the check I built to stop numeric drift was the thing that
proved it.

### Certification — 77 checks, 0 failures, 1 honest gap

Re-run after cycle 15, against `master` with every repair merged: **77 passed, 0
failed, 1 reported NOT MECHANICALLY VERIFIABLE.**

**The certification was verified to discriminate**, which the first one never
was. Reverting #511's one-line key turns **5 of the 77** red — the one-rule
assertions by name, plus the full-suite criterion. A certification that cannot
fail is what produced 36/36 over five false criteria.

**The count moved because the certification's scope did, and that is its own
finding.** The script had the milestone's issue numbers written into it, so once
#540, #541 and #546 were admitted it was silently checking a stale population —
reporting "all 13 scope issues report CLOSED" about a milestone holding sixteen.
That is #546's defect one level up, in the instrument that certifies the fix for
it. The scope is now derived from the milestone and the run aborts if the query
returns nothing, because a certification over an empty population would pass
every per-issue criterion vacuously.

**The honest gap is the gate's own disposition.** #478 declares `operator`,
`roadmap` and `release`, and **neither evidence mode can reach them**:

- the linked-PR mode needs a **closing** PR, and closing a release gate is a human
  act, not a merge;
- `--branch` needs an **open** branch carrying the change, and the gate's
  documentation has already merged.

PR #542 changed exactly those three surfaces, so the work exists in the merged
history. It is simply unreachable from the issue.

An earlier run of this certification recorded the `--branch` verdict as PASS. That
was true only because the certification branch happened to still carry those
files; on a fresh branch it FAILs. **Manufacturing a branch that re-touches them
would turn the check green while proving nothing** — the move that makes a report
better and the repository worse — so it is reported as unverifiable instead. Same
family as #524 and #539: what the evidence set can reach, rather than how it is
graded.

`--branch` is deliberately *not* used for the other thirteen issues. It unions the
current branch's diff, so running it from an unrelated branch would let this
certification's own changes satisfy any issue's declaration — a real false pass,
and avoiding it matters more than a greener number.

**The harness de-authenticated `gh`, and 34 live checks silently returned

first run reported 34 failures with empty values. They failed loudly only because

contain X" would have passed on emptiness and certified against no evidence at

does.

**#470 was over-declared, by me, under pressure from the verb.** It carried
`docs-impact:operator` because the run's ledger rode in the same branch during its
re-audit — so the declaration described the *PR* rather than the *issue*. Its
implementation, PR #505, changed reference and architecture; the ledger is the
run's record. Narrowed back, and it now PASSes on truth rather than on a
workaround. The same pressure widened eleven issues before it was noticed, and is
filed as **#539**.

**Six open issues carried no release disposition** — #524, #526, #530, #535, #539
— and `spark governance apply` reported each one. They are backlog by intent, so
they now say so. A governance finding about the run's own output, produced by the
tool under test.

### The finding that outlasts the milestone

The first certification passed **36 of 36 checks while five criteria were false**.
Nothing was fabricated; every check ran. They were simply checks of the wrong
thing — a function's name, a comment's text, a command's exit code in an
environment that happened to have `gh`.

The repair run therefore imposed one rule: *a grep for a function name, a comment
string, a command name or a documentation phrase is not evidence that the
corresponding property holds.* Applying it produced findings in every single
cycle, and — more tellingly — it produced findings in the instruments themselves:

- an audit harness that inherited `set -e` from the binary it sourced, so the
  first red criterion silently ended the run;
- a no-`gh` fixture that enumerated tools instead of removing one, and
  manufactured two failures that did not exist;
- a forbidden-token check that fired on the fix's own explanatory prose;
- an exit-code assertion that passed because something *else* in the run produced
  the same code;
- an order fixture with one ordered child, where relative order is trivially
  correct and no wrong answer could exist;
- an audit assertion that overreached its criterion, and would have justified
  changing tested, deliberate behaviour to make an audit green.

The last one is the most dangerous, because it points the wrong way: it would have
made Spark worse in order to make a report better.

### The two-authority pattern

Four of the eight defects had one shape: **two implementations of one rule.** The
per-member `exclusive` key; `cmd_docs_impact`'s private copy of the exclusivity
verdict; the `update` validator's own `#N` test; `spark next`'s hard-coded
`P0 P1 P2 P3` fallback.

In every case the second implementation was *shorter* than the first, looked
obviously correct in isolation, and disagreed only on inputs nobody had tried.
Three of the four took over precisely when the first authority was unusable —
which is the worst possible moment for a silent substitute.

That is the defect class this milestone exists to remove, and it kept appearing
*inside* the work removing it. Governance as schema is not finished when the
schema exists; it is finished when nothing else answers the same question.
