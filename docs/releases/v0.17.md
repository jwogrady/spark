## Why this milestone cuts no version

`master` already carries the cumulative implementation through the reconstructed
v0.19 outcome. Cutting a fresh `v0.17.0` from current `HEAD` would place v0.18
and v0.19 implementation inside a tag named `v0.17.0`, and reduce the later
releases to governance-only — recreating the release/scope mismatch that the
2026-08-26 rollback corrected.

The implementation is therefore **not deferred and not lost**. It reaches the
public once, inside the cumulative **`v0.19.0`** catch-up release, gated by #445.
See `v0.19.md`.

## v0.17's failure mode: premature certification, not missing governance

This distinguishes v0.17 from v0.18 and v0.19, where the planning structure was
absent. **Do not flatten the three into one story.** Every v0.17 planning
artifact existed *before* publication:

| Artifact | Evidence |
| --- | --- |
| Milestone | #14, created 2026-08-12T19:50:07Z |
| Release-readiness gate | #373, created 2026-08-12T19:38:44Z |
| Roadmap entry | `ROADMAP.md` carried a `## v0.17 — Provenance promotion` section |
| Release plan | `v0.17-plan.md`, merged by PR #378 as commit `333b85bb` |
| Issues | #372, #374–#377, #380 filed and milestone-assigned |

`v0.17.0` published 2026-08-13T00:57:25Z — after all of the above.

The defect was the release boundary and its certification. #373 was closed as
`completed` so release PR #382 could go green, and **#389 proved that closure was
wrong**: the Cosmos dogfood had not reached a durable record, the generated notes
were not one entry per logical change, and #385 — a release-scope correctness
defect — was still open.

So v0.17 is the case where the governance **existed and was overridden**.

## The reconstructed scope is wider than the withdrawn tag

Those deliver v0.17's own stated criteria, which is why #393 is a member of this
milestone alongside #385 even though its fix shipped in what was then v0.18.0.
The withdrawn tag boundary is evidence, never version authority.
