## Nomination 1: Resolve the LICENSE file — adopt or disclaim the MIT license

**Priority: P1**

**Case:**
`plugin.json` declares `"license": "MIT"` and the README badge displays MIT, but
the actual `LICENSE` file reads: *"License TBD. Copyright belongs to the author."*
No enforceable open-source license is currently in place. Any downstream user
who reads the manifest or badge and proceeds to incorporate, redistribute, or fork
Spark is acting on a false signal — MIT has not been granted. This is a legal
integrity problem, not a polish issue. Until the `LICENSE` file is formally
updated to a real SPDX license text (or a clear proprietary declaration), the
manifests and docs must not display a license badge, and the install docs must
carry a disclaimer. This is the single highest-trust-risk item in the repo and
the only one that could expose users to real legal uncertainty.

**Provenance:**
`04-trust.md` § "License status" — "No enforceable open-source license is in
place. `plugin.json` declares MIT; `LICENSE` file reads 'License TBD.'" Raised
first in `00-ground-truth.md` § "Accuracy flags" — "License mismatch. `plugin.json`
declares `"license": "MIT"` and the README badge says MIT, but the `LICENSE` file
contains only 'License TBD. Copyright belongs to the author.' — the manifests
overclaim a license the repo has not actually adopted." Also surfaced in cross-eval
from `03-positioning.md` (feedback item 8: "Add license mismatch concession").

## Nomination 2: Add a CI workflow for `spark doctor` and shell-script syntax checks

**Priority: P2**

**Case:**
There is no `.github/workflows/` directory and no automated test files in the
repository. `spark doctor` and `bash -n` syntax checks are the current quality
gates, but they run only when the author remembers to invoke them — nothing
enforces them on push or pull request. For a project whose entire correctness
surface is valid JSON, well-formed Markdown frontmatter, and syntactically clean
Bash, a minimal CI workflow (run `spark doctor` + `bash -n` on every push/PR)
would catch regressions automatically and provide the CI badge that evaluators
expect. The absence of any CI signal is a real contributor barrier: someone
considering a pull request cannot know whether their change passes the project's
own quality checks without running the CLI locally. The enforcement model is
deliberately mechanical in the runtime (hooks), but the CI gap is a gap — it is
not a deliberate architectural choice to have zero automated regression on push.

**Provenance:**
`04-trust.md` § "CI / automated testing" — "No CI workflows exist. There is no
`.github/workflows/` directory. There are no automated test files in the
repository." Confirmed by `bash: ls .github/workflows/ → NO_WORKFLOWS_DIR` and
`bash: find . -name "*.test.*" -o -name "*.spec.*"` with no output. Trust note
also states: "The honest gap remains: no automated regression on skill behavior
or CLI output. This is a real limitation for contributors." The badge row analysis
(`04-trust.md` § "Badge row") explicitly marks CI as "NOT READY — omit until CI
exists."

## Nomination 3: Enter `codify` and `review` skills into CHANGELOG.md

**Priority: P2**

**Case:**
The `codify` crew (6 agents under `agents/codify/`, `skills/codify/SKILL.md`) and
the `review` skill (`skills/review/SKILL.md`, 8-agent audit) are verified, shipped
features documented in `00-ground-truth.md`. Neither appears in the `[Unreleased]`
section of `CHANGELOG.md`. The changelog lists `docit` in detail but omits these
two skills entirely, making it an inaccurate record of what the current HEAD
contains. This is a maintenance gap that will cause downstream confusion when a
v0.3.0 release is tagged: the release notes will either silently omit the codify
and review capabilities or require a retroactive edit. Maintaining the changelog
current with the repo is the contract established by the `[Unreleased]` block and
the Keep-a-Changelog format the project declared. The commits `6ea36a7 feat: add
codify internal-knowledge crew` and `de7b9f9 feat: add review skill` are both in
the unreleased window (`git log v0.2.0..HEAD`) and have no corresponding changelog
entries.

**Provenance:**
`04-trust.md` — cross-eval feedback from 09 (Returning User) and from Evaluator
feedback-to-09 (`feedback/from-04-to-09.md` Issue 1): "`codify` is NOT in
`CHANGELOG.md` — the headline claim is unsupported." Verified by reading
`CHANGELOG.md` in full (69 lines, no codify entry) and by `git log v0.2.0..HEAD`
showing `6ea36a7 feat: add codify internal-knowledge crew` and
`de7b9f9 feat: add review skill` in the unreleased window. Also supported by
`00-ground-truth.md` § "Review / knowledge skills" — both `review` and `codify`
are listed as SHIPPED features.

## Nomination 4: Document a breaking-change policy for pre-1.0 releases

**Priority: P3**

**Case:**
Spark is at v0.2.0 with no documented policy on what constitutes a breaking change
or what callers can expect across `v0.x` bumps. CLAUDE.md states "One logical
change per commit" and the commit hook enforces conventional types, but there is
no CHANGELOG entry, README section, or doc explaining what breaking-change
discipline the project intends to follow before a 1.0 declaration. Callers who
install Spark today and update it in the future (once a published marketplace
listing exists) have no stated contract. This is a pre-1.0 norm, not a blocker,
but naming it explicitly — even as "treat any v0.x release as potentially
breaking" — converts an ambiguity into a documented commitment. The trust note
already states this verbally in the maturity statement; the gap is that it does
not appear in any user-facing doc or README.

**Provenance:**
`04-trust.md` § "Maturity statement" — "No breaking-change policy is documented;
callers should treat any `v0.x` release as potentially breaking." The ROADMAP
(`00-ground-truth.md` § ROADMAP section) lists milestones through v0.5 but none
address API or skill-contract stability. The README currently has no stability /
breaking-change section. This was not flagged in cross-eval feedback, making it
a Evaluator-originated finding with no duplicate risk from other personas.
