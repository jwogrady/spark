# Issue Council Nominations — 02 Adopter

**Persona:** Adopter (install + quickstart)  
**Phase:** 4 — Issue Council Nomination

## Nomination 1: `spark doctor` Output Format Unverified

**Title:** `spark doctor` output format claims not in ground truth

**Case:** The quickstart instructs newcomers to run `spark doctor` and expect "all 16 skills listed as ✓ and all docit/codify agents verified (13 + 6 = 19 agents)." Ground truth documents that `doctor` validates these items but does not describe the actual CLI output format. When a newcomer runs the command and sees different formatting, they lose trust immediately — the guide promised specific output but delivered something else. This is a honesty-hype contract violation that erodes the first-win experience.

**Provenance:** Feedback from personas 00 (Cartographer), 03 (Skeptic), 06 (Coach), 08 (Visual Storyteller) all independently flagged this. Ground truth `00-ground-truth.md` lists `doctor`'s validation capabilities but does not cite its output format. No transcript or observed output exists in ground truth to verify the "✓ … 16 skills" and "19 agents" text.

**Proposed priority:** P1 (blocks newcomer trust and verification step)

## Nomination 2: Marketplace Install Incomplete — v0.2 Open Item Buried

**Title:** Quickstart advertises marketplace install but it's unverified end-to-end

**Case:** The install section presents `/plugin marketplace add jwogrady/spark` as the primary path, with no caveat about the v0.2 open item ("validate install end-to-end from a *published* marketplace — unchecked box"). A newcomer who follows this path may find the plugin is not yet in the official marketplace or behaves differently than advertised. This breaks the premise: "install once, carry it everywhere." The caveat exists in ground truth but is buried and not prominent enough in the quickstart.

**Provenance:** Feedback from persona 03 (Skeptic) and 01 (Skimmer) flagged the missing caveat. Ground truth `00-ground-truth.md` ROADMAP section explicitly states: "v0.2 open item: validate install end-to-end from a *published* marketplace (unchecked box)." This is a mechanical, verifiable gap — the marketplace listing is not complete.

**Proposed priority:** P1 (blocks install path for newcomers; prevents adoption if marketplace is not populated)

## Nomination 3: GitHub CLI Prerequisite Under-Documented

**Title:** `/spark:ship` requires `gh` CLI auth but it's a hidden prerequisite

**Case:** The quickstart walks a newcomer through the full Ideate → Ship cycle but does not upfront flag that PR creation (the final step) requires GitHub CLI (`gh`) to be installed and authenticated. A newcomer who reaches `/spark:ship` without `gh auth login` will fail at the push step, breaking the promised "complete cycle in one session." The prerequisite exists in the quickstart footnotes but is not prominent enough for the happy path.

**Provenance:** Feedback from personas 01 (Skimmer), 08 (Visual Storyteller) flagged the `gh` auth complexity. Ground truth does not document `gh` as a verified Spark dependency (it's a system-level integration), but the hero promise ("ready in minutes") implicitly assumes GitHub auth is already set up. A fresh user setting up Spark for the first time will not have this pre-configured.

**Proposed priority:** P1 (blocks final stage of the promised Ideate → Ship cycle)

## Nomination 4: `/spark:plan` GitHub Issue Creation Not Shipped in v0.2

**Title:** Quickstart claims `/spark:plan` creates GitHub issues, but it's v0.3 roadmap

**Case:** The quickstart instructs a newcomer to run `/spark:plan` and expect "Spark will decompose it into 2–5 GitHub issues with acceptance criteria and create a milestone." Ground truth explicitly lists GitHub issue creation as a v0.3 roadmap item ("Plan ↔ GitHub — generate issues/milestone from a problem statement"). In v0.2, the skill may generate issue drafts or templates, but direct GitHub integration is not mechanical. This breaks the happy path: a newcomer follows the cycle and discovers the plan step does not create real GitHub issues.

**Provenance:** Feedback from persona 08 (Visual Storyteller) flagged the v0.3 ROADMAP conflict. Ground truth `00-ground-truth.md` ROADMAP section explicitly states the feature is planned for v0.3, not shipped in v0.2. The quickstart does not cite this caveat.

**Proposed priority:** P1 (breaks the complete Ideate → Plan → Ship happy path in a single session)

---

## Nomination 5: Missing Upfront GitHub Auth as Prerequisite

**Title:** Hero promise "ready in minutes" does not mention GitHub CLI setup

**Case:** The hero persona (01-hero.md) promises "Install it once, every project gets the same lifecycle" and implies a newcomer can complete a full cycle in one focused session. But the quickstart reveals that `/spark:ship` requires `gh auth login`, which is not mentioned in the hero hook. For a newcomer without GitHub CLI already authenticated, this is a 2-3 minute setup detour that breaks the "ready in minutes" promise. The prerequisite should be called out upfront in the hero hook or the quickstart should de-emphasize the "complete cycle in one session" claim.

**Provenance:** Feedback from persona 01 (Skimmer) noted the hero over-promises relative to the auth complexity. Ground truth does not list `gh` auth as a prerequisite; it's a system-level assumption. The hero makes no mention of any prerequisites.

**Proposed priority:** P2 (delays first win but doesn't block it; ~2-min setup)

---

## Nomination 6: `spark doctor` Output Format Not Documented for Scripting / CI

**Title:** `spark doctor` contract is unclear — no documented exit codes, output schema, or machine-readable format

**Case:** A newcomer who wants to use `spark doctor` in CI or a setup script cannot rely on its output format because it is not documented. Ground truth only describes the validation logic, not the output contract (exit codes, lines per item, error message format). This forces users to either reverse-engineer the tool or avoid automation, complicating adoption in team setups.

**Provenance:** Ground truth `00-ground-truth.md` CLI section documents `doctor` validation behavior but not its output contract. Personas 00, 03, 06, 08 all flagged the output format over-promise in the quickstart, indicating the contract is not clear enough for public documentation.

**Proposed priority:** P2 (blocks team/CI adoption but not single-user first win)
