# Issue Council Nominations — Persona 07 (Contributor)

Four nominations from the Contributor domain: the extension path, contribution
standards, and "start here" guidance for new contributors.

---

## Nomination 1 — Resolve conflicting optional skill layout specs

**Title:** Canonical optional skill layout is undefined — two specs conflict, blocking `write-a-skill` how-to

**Case:**
`CONTRIBUTING.md` §"Proposing a skill" specifies the optional subdirectory layout
as `references/` and `agents/`. `skills/write-a-skill/SKILL.md` specifies
`REFERENCE.md`, `EXAMPLES.md`, and `scripts/`. These are two different structures
in the same repo for the same concept. A contributor authoring a new skill has no
single authoritative source for what the optional layout looks like. Worse, the
`write-a-skill` how-to (`docs/how-to/write-a-skill.md`) cannot be written
accurately until this is resolved — it would have to pick one spec or fabricate a
third. This inconsistency is a blocker for downstream doc work and for any
contributor who tries to scaffold a non-trivial skill. The fix is one decision
(pick the canonical spec), one update to whichever source is out of date, and then
the how-to can proceed.

**Provenance:** Raised in `07-contributing.md` cross-eval and confirmed in
`06-diataxis.md` §Mode 2 How-to gaps ("Canonical skill layout spec needed — HIGH —
BLOCKING"). Both notes trace to the source conflict: `CONTRIBUTING.md` §"Proposing
a skill" vs. `skills/write-a-skill/SKILL.md` (verified files, confirmed in
`00-ground-truth.md` §Setup/inception skills entry for `write-a-skill`).

**Proposed priority:** P1

## Nomination 2 — Create `docs/how-to/write-a-skill.md`

**Title:** No human-readable how-to for skill authorship — contributors are routed to an AI instruction set

**Case:**
`07-contributing.md` §"Your first contribution" currently directs contributors to
"follow the patterns in `skills/write-a-skill/SKILL.md` until [a how-to] does
[exist]." That is an honest acknowledgment of a gap, not a solution. `SKILL.md`
files are AI instruction sets — they describe what Claude Code should do, not what
a human contributor should do step-by-step. Routing a new contributor to a
`SKILL.md` as their primary authoring guide is misleading and will produce
confusion. The `write-a-skill` how-to is the single most impactful doc addition
for the contribution path: skill authorship is the canonical extension mechanism,
and there is currently no human-targeted task guide for it. This nomination is
directly downstream of Nomination 1 — the how-to cannot be accurate until the
canonical layout is resolved, so these two issues should be created and linked.

**Provenance:** `07-contributing.md` §"Your first contribution" bullet 1 (explicit
gap acknowledgment); `06-diataxis.md` §Mode 2 How-to gaps ("No `write-a-skill`
how-to — Medium — partially covered by `CONTRIBUTING.md`; BLOCKED by layout
inconsistency"). `00-ground-truth.md` §Docs confirms no `docs/how-to/write-a-skill.md`
exists in the verified docs tree.

**Proposed priority:** P2 (unblocked after P1 resolves)

## Nomination 3 — Document branch naming convention in the contribution how-to path

**Title:** Branch naming convention exists in `CONTRIBUTING.md` but is absent from the docs/ how-to tree

**Case:**
`CONTRIBUTING.md` §"Branches" documents four branch-naming conventions
(`feat/`, `fix/`, `docs/`, `chore/`). This information is at the repo root and is
not surfaced in the `docs/how-to/` tree, meaning a contributor navigating docs
will not encounter it. More importantly, `07-contributing.md` does not mention
branch naming at all — a contributor reading the contribution note would follow
the skill-authorship scaffold, run `spark doctor`, and open a PR, all without
knowing the expected branch naming pattern. The `commit-msg` hook enforces the
conventional-commit prefix, but no mechanical enforcement covers branch names,
so the only gate is human knowledge. The fix is lightweight: add the four naming
patterns as a step in the contribution scaffold in `07-contributing.md`, and
ensure the how-to covers it. This was flagged in the `from-05-to-07` cross-eval
(Principle 6, Issue 3 — terminology gap on branch naming noted, marked "NOTED,
no action on 05; logged for persona 07").

**Provenance:** `05-philosophy.md` Cross-eval §from-07-to-05 Issue 3 ("terminology
gap on branch naming — flagged for 07's own revision: NOTED"); `CONTRIBUTING.md`
§"Branches" (four naming patterns verified by reading the file); `07-contributing.md`
§"Work on a feature branch" step — mentions feature branch but omits the naming
patterns. `00-ground-truth.md` §"Development Workflow" and §CLAUDE.md §"Development
Workflow" confirm one-concern-per-branch policy but do not name the branch patterns.

**Proposed priority:** P3

## Nomination 4 — Fix `README.md` "What's in the box" CLI list (omits `list-skills`)

**Title:** README undercounts CLI subcommands — `list-skills` is verified-real but absent from the feature list

**Case:**
The `README.md` "What's in the box" section lists the `spark` CLI subcommands as
`doctor, new-skill, install-git-hooks, shred-env, help` and omits `list-skills`.
`list-skills` is a real dispatch case in `bin/spark` (`cmd_list_skills` function,
verified). This is a factual undercount on the primary discovery surface for the
project. For a contributor evaluating Spark, the README is the entry point — a CLI
command that is invisible in the README is effectively undiscoverable until you run
`spark help` or read the source. The fix is a one-line addition to the README CLI
table. It is low-effort and directly addresses a known accuracy flag.

**Provenance:** `00-ground-truth.md` §"Accuracy flags" — "README 'What's in the
box' lists the CLI as `doctor, new-skill, install-git-hooks, shred-env, help` but
omits `list-skills`, which is a real dispatch case in `bin/spark`." Also confirmed
in `06-diataxis.md` §Mode 3 Reference gaps ("list-skills missing from CLI reference
— Low — accuracy fix").

**Proposed priority:** P3
