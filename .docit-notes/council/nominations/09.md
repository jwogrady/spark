## Nomination 2: No upgrade testing for git hook changes

**Title:** Document git hook compatibility and add validation step for users with custom hooks

**Case:** `04-trust.md` notes "no CI / automated testing" (line 36), and while the trust persona correctly frames enforcement hooks as intentional architecture (not a testing gap), there is a real upgrade risk for users who have customized their `.git/hooks/` files in their own projects. The plugin ships `scripts/hooks/commit-msg` and `scripts/hooks/pre-commit` that can be installed via `spark install-git-hooks`. If a user has a pre-existing hook (e.g., a linter, Husky config, or custom company automation), the `install-git-hooks` command "refuse[s] to overwrite a non-Spark hook" (`00-ground-truth.md` line 55), but there is no documented upgrade path for users with custom hooks beyond "if you hit this, you lose Spark's enforcement."

The changelog says "no repo changes needed" (09-changelog.md), which is true at the plugin level but misleading for users who may have custom hooks. This is a breaking-change silent failure.

**Provenance:**
- Ground truth: `00-ground-truth.md` line 55 — `install-git-hooks` refuses to overwrite non-Spark hooks.
- Ground truth: `00-ground-truth.md` line 48 — Enforcement hooks block force-push and trunk pushes.
- 09's changelog draft (09-changelog.md line 79): "No repo changes needed" — true but incomplete for hook users.
- 04-trust.md: enforcement posture is intentional architecture; upgrade docstring is missing.

**Proposed Priority:** **P2** (documentation + defensive migration note). Not a code change needed, but the upgrade path must address users with custom hooks: either a clear "you keep your hooks, Spark enforces at plugin level" statement, or a recommended merge/coexistence pattern (pre-commit hooks can chain).

## Nomination 3: License mismatch unresolved in `CHANGELOG.md`

**Title:** Clarify license status in release notes (TBD) or block until license file is adopted

**Case:** `04-trust.md` (line 31) calls the license mismatch "the single highest-trust risk in the repo": `plugin.json` and README badge declare MIT, but the `LICENSE` file reads "License TBD. Copyright belongs to the author." The `09-changelog.md` upgrade path (line 61) instructs users to reinstall with `/plugin marketplace add jwogrady/spark`, but makes no mention of this risk. An existing user reading upgrade notes will not know they are adopting a project with no enforceable open-source license. This is honest-hype violation: the changelog must surface the license risk or the release must be blocked until the risk is resolved.

**Provenance:**
- Ground truth: `00-ground-truth.md` "Accuracy flags" section (lines 142–145) — manifests overclaim an MIT license the repo has not adopted.
- 04-trust.md line 31 (Phase 2 cross-eval, verified): "No enforceable open-source license is in place. Do not incorporate Spark into a project with legal review requirements until a license file is formally adopted."
- 09-changelog.md line 61: upgrade path makes no mention of license risk.
- Current repo state: `LICENSE` file still reads "License TBD."

**Proposed Priority:** **P1** (adoption blocker, legal risk). Users cannot make informed upgrade decisions without knowing the license status. Either update `CHANGELOG.md` Unreleased to explicitly call out the license risk ("License: TBD — see `LICENSE` file; not enforceable as MIT yet") or defer this release until a formal license is adopted.

## Nomination 4: CLI `list-skills` undercounted in upgrade narrative

**Proposed Priority:** **P3** (documentation completeness). Low user friction, but adds clarity to available tooling. Could be addressed via a simple added line in CHANGELOG.md or a note in the README CLI section.
