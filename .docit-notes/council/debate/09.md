### Upgrade path for users with custom git hooks (P2)

**Nominator:** 09-Returning User (N09-2).

**My position:** **Admit and vote P2.** Ground truth documents that `spark install-git-hooks` "refuse[s] to overwrite a non-Spark hook." This is a good safe default. But an existing user who upgraded Spark and then runs `/spark:commit` might find that their custom hook (e.g., Husky, linter, pre-commit) is still active and Spark's hooks are not installed. They have no documented path to coexist. My upgrade notes said "no repo changes needed," which is true at the plugin level but misleading for hook users. The migration gap is: either (a) "you keep your hooks, Spark enforces at plugin level" must be stated plainly, or (b) a recommended coexistence pattern (pre-commit hooks chain cleanly).

**Action:** Document the hook coexistence model in the upgrade section of the next CHANGELOG or in a hook-migration how-to.

## Contested Positions (What I Push Back On)

### Marketplace install caveat framing (P2 → P1 debate)

**Nominators:** 01-Skimmer (issue 4), 02-Adopter (issue 2), 03-Skeptic (issue 1), 06-Coach (via 02's note), 11-Amplifier (issue 4).

**My position:** **Admit, but contest priority framing.** The caveat is real and honest: v0.2 has an unchecked marketplace-install box. My Phase 3 changelog correctly stated: "Reinstall: `/plugin marketplace add jwogrady/spark`" with an implicit assumption users have a fallback (Git URL). But four nominators flag that the README install block presents marketplace as primary with no fallback visible. For an *existing user* upgrading, this is less critical than for a *new user* installing from scratch. An existing user likely has Spark already, and the upgrade path (reinstall the plugin) is agnostic to marketplace vs. local. A new user hits the README and finds no fallback.

**My reframing:** Admit as P2 for *upgrade readiness*, but note that P1 status belongs to the install how-to / README, not to the CHANGELOG. The changelog's job is to surface what changed and how to move forward; the README's job is to surface the fallback install path. Don't conflate them.

**Action:** Fix the README install block (add Git-URL fallback), not the CHANGELOG. The CHANGELOG can acknowledge the caveat without inflating its priority.
