## My Co-Signed Admissions (I concur entirely)

### 1. **MIT license mismatch (everyone flags this) — P1 CRITICAL**

**Co-sign with full weight.** N00-1, N01-2, N03-2, N04-1, N05-3, N09-3, N10-4, N11-1 all nail the same blocker: `plugin.json` declares MIT, `LICENSE` says TBD, README badge says MIT. This is not a documentation tweak — it's a **legal overclaim that a newcomer discovers in the first 30 seconds when they read the `LICENSE` file after installing from the marketplace.** That moment is catastrophic for trust.

**Why it blocks the happy path:** A newcomer who follows `/plugin install spark` and then looks at the repo to understand what they installed finds contradictory legal signals. The `LICENSE` file is the first place they look for legal terms. Seeing "TBD" next to a manifest that says "MIT" is a immediate trust failure. Cannot proceed.

**Evidence:** Multiple personas independently verified: manifest reads `"license": "MIT"`, `LICENSE` file reads "License TBD. Copyright belongs to the author."

**My vote:** Admit, P1. Fix before any launch.

---

### 2. **Marketplace install is unverified in v0.2 — missing caveat in README (P1 blocker for newcomers)**

**Co-sign with weight.** N01-4, N02-2, N03-1, N04-3, N10-4, N11-4 (different framings, same gap).

**Why it blocks newcomers:** The README install section presents `/plugin marketplace add jwogrady/spark` with zero caveat. The ground truth explicitly says v0.2 has an open item: "validate install end-to-end from a *published* marketplace (unchecked box)." A newcomer blindly copies the install command, the marketplace listing does not exist (or is incomplete), and they hit a dead end with no fallback instruction. The caveat exists in my quickstart draft and in the hero note's cross-eval feedback but **never landed in the README itself.**

**The honest fix:** README install block should read: "Install (from a local clone or Git URL; marketplace listing coming in v0.3)." One line. Adds honesty, zero complexity to the path.

**Evidence:** ground truth ROADMAP section; multiple personas (01, 03) noted the revisions happened in hero/quickstart but README was never updated.

**My vote:** Admit, P1. This is a newcomer-facing install gap with a known fix.

### 3. **`spark doctor` output format overclaimed but not verified (P1 for honesty)**

**Co-sign.** N02-1, N00-4 (Cartographer and I both flagged this).

**The problem:** Multiple drafts (my quickstart included) describe `spark doctor` output that does not exist in ground truth. The Cartographer read the actual `bin/spark` and found: doctor emits a green `✓ <name>` per skill, then `Healthy — 0 errors, N warning(s)`. I promised newcomers a "16 skills verified" tally line. That output does not exist. 

**Why I co-sign my own finding:** As the Adopter, I promised newcomers copy-paste commands that actually work. If I told them `spark doctor` outputs "16/19 verified" and they run the command and see `✓ ideate`, `✓ plan`, etc., then `Healthy — 0 errors`, **they will not see the promised tally.** That is a honesty-hype contract violation. The command *works*, but what I promised they would see is false. I must strike that language from the quickstart.

**My vote:** Admit, P1. The output format must be verified and quoted accurately or removed entirely from quickstart copy.

### 4. **GitHub CLI (`gh`) auth prerequisite is hidden — P1 for newcomers**

**Co-sign.** N02-3, N02-5 flag this (I flagged it in my own feedback).

**The problem:** The promised "complete Ideate → Ship cycle in one session" requires `/spark:ship` which requires `gh auth login` (GitHub CLI). A newcomer without `gh` already authenticated will fail at the final step with "not authenticated." This is a **hidden prerequisite that breaks the first-win promise.**

**Why it's real:** The quickstart walks through Ideate → Plan → Build → Solve → Ship. By Ship, a newcomer expects success. They hit `gh: not authenticated` and the cycle breaks. I flagged this in Phase 2 feedback and it belongs in Council.

**The honest fix:** Either (a) call out upfront: "You will need GitHub CLI authenticated (`gh auth login`)"; or (b) de-emphasize "complete cycle in one session" and stage the path as: today = Ideate through Solve; tomorrow = Ship.

**Evidence:** Persona 01 noted the hero overshoots ("ready in minutes") given the auth friction.

**My vote:** Admit, P1. This is a blocker for the promised happy path.

## My Contested Positions (I veto or reframe these)

### 5. **`/spark:plan` creates GitHub issues — N02-4 (VETO as currently framed)**

**Contest:** This is not a newcomer install/quickstart blocker — it is a **feature-expectation mismatch that belongs in a *design* issue, not a launch blocker.**

**Why I contest it:** The quickstart I wrote says `/spark:plan` decomposes the problem into GitHub issues. Ground truth lists this as a v0.3 roadmap item. So yes, there is a gap: in v0.2, `/spark:plan` does not create mechanical GitHub issues. But this is not a *missing install step* or *broken prerequisite.* It is a feature promise mismatch.

**The honest framing:** This should be a GitHub issue ("Plan skill: integrate GitHub issue creation v0.3"), not an Issue Council admission under my domain. My domain is **install + quickstart**; this is **feature planning.** If we admit this under "blocks newcomer first win," we are saying "a newcomer cannot succeed without GitHub issues being created." But the actual first win is much simpler: run the full cycle, learn the lifecycle, and discover that Plan generates drafts, not live issues. That is honest and achievable today.

**My vote:** Contest. Reframe as a feature gap, not a quickstart blocker. If the orchestrator insists on Council admission, I recategorize it as *low priority* because it does not break the install/quickstart path — it breaks a feature promise.

### 7. **`docs/tutorials/set-up-a-new-project.md` (N06-C) — contextualize the priority**

**Nuanced co-sign:** This tutorial gap is real and I am downstream of it (my quickstart assumes someone has already bootstrapped). But I contest the P1 rating **for a newcomer with zero prior context.**

**Why:** A true blank-slate newcomer follows the README install steps, clones a repo, and runs `/spark:ideate`. They do not run `spark bootstrap` or `spark connect` first. The setup skills are for *project inception*, not *adopting Spark as a plugin.* The tutorial gap is real for the "start a new project from Spark seed" path, but that is different from "install the plugin into an existing project" (my path).

**The honest split:** Tutorial 1 (set-up) is P2 (needed for project-inception path); Tutorial 2 (first project) is my prerequisite, and it exists. My quickstart assumes the reader is already in a project and has Claude Code + Spark plugin installed.

**My vote:** Co-sign the issue, reframe as P2 (not P1), and clarify in the issue description that this is for the "new project from Spark seed" path, not the "install Spark into an existing project" path.

### 8. **Missing `spark doctor` demo GIF (N08-1) — honestly argue it's not a blocker**

**Contest as P1, argue for P2.** The Storyteller calls this a "must-ship asset" and a "launch blocker." I disagree.

**Why it's not a newcomer blocker:** A newcomer runs `spark doctor` in their terminal. They see the output live. They don't need a GIF to verify it works — they ran it. The GIF is nice-to-have for the README web view, but it is not a blocker for someone installing and running the command. The README can say "Run `spark doctor` to verify your setup" without a GIF and the newcomer will still succeed.

**Trade-off:** Creating a GIF is effort. The happy path does not require it. Better to ship a README that works and add the GIF in a follow-up PR than to block release on it.

**My vote:** Contest as P1. Admit if others insist, but I argue P2 (nice-to-have for marketing, not for the install cycle).

## My Strongest Positions (What the Council Must Hear)

### **Position A: Install path honesty is non-negotiable**

The MIT license mismatch and the marketplace install caveat are not polish issues. They are **credibility failures at the moment a newcomer discovers them.** When someone installs a plugin, the first things they read are:

1. The manifest / plugin info
2. The README
3. The LICENSE file

If those three documents contradict, the newcomer concludes: "This project is not ready" or "I cannot trust the author." Both are fatal for adoption. These two issues (license + marketplace caveat) must be resolved before announcing Spark publicly.

**Council resolution target:** Both should be **admitted and scheduled before launch.**

---

### **Position B: Prerequisite honesty is critical**

The `gh auth` prerequisite hidden in the Ship step is a **silent failure mode.** A newcomer follows the happy path, gets almost to the finish line, and hits "gh: not authenticated." They think they did something wrong. That is a horrible first experience.

**Council resolution target:** Either document the prerequisite upfront in the README install block, or stage the quickstart to separate it. Either way, admit N02-3 and schedule it.

---

### **Position C: Claimed output must be verified before promising**

I made a mistake in my quickstart draft: I promised newcomers would see "16 skills / 19 agents verified" in the doctor output. The Cartographer caught that this is false. That is why we have the honest-hype contract. I cannot ship a quickstart that describes unverified output.

**Council resolution target:** Either (a) verify the actual `spark doctor` output and quote it accurately, or (b) remove the output-specific language and just say "Run `spark doctor` to verify."
