# Issue Council Debate — Persona 03 (Skeptic)

> Author: jwogrady
> Phase: 4 — Issue Council: Debate
> Persona: Skeptic (positioning, honest comparison, honest-hype guardian)

The Skeptic's job is to call overclaims before they ship and make sure the
signal-to-noise ratio in this issue list is high. I read all 12 nomination files
and I'm arguing my positions below.

---

## A. Strong co-signs (add weight)

### A1. License mismatch (N00-1, N01-2, N03-2, N04-1, N05-3, N09-3, N10-4, N11-1)

Eight personas nominated the same defect. Every single one of them is right.
I nominated it myself (N03-2) as P1. My additional weight here is specific:
from a positioning standpoint, a green MIT badge *above the fold* is the single
strongest trust signal a developer reads before deciding whether to install. It
is also the first thing they verify when they want to redistribute. The MIT badge
and the "License TBD" file are in direct contradiction on the most legally
sensitive surface in the repo. This is not a documentation polish issue; it is an
active overclaim. If this ships unresolved, any comparison table, any "vs.
alternatives" doc, and any launch copy that notes the license must carry a live
caveat. Every other piece of marketing work is hostage to this one unfixed file.

**Position:** P1, hard blocker. Must resolve before any marketing, awesome-list,
or launch distribution. Merge all eight nominations into a single issue.

### A2. Marketplace install caveat (N01-4, N02-2, N03-1, N11-4)

I filed N03-1 as P1 and I'm co-signing every other nominator on this. The README
is the only public-facing surface that does not carry the caveat. My positioning
note, the hero note, the launch copy, and the HN blurb all concede it. The README
does not. The blast radius: a developer who reads *only* the README (the most
common case) will try the marketplace install, hit a dead end, and associate
the failure with Spark rather than with the unfinished marketplace. That is the
worst possible first impression for a positioning note that argues "portability
and enforcement."

**Position:** P1. Single issue — add the Git-URL fallback and the v0.2 open-item
note to the README install block. Four nominations → merge into one.

## B. Contests (duplicate, out of scope, or low value)

### B1. Contest: N06-C (Tutorial 1 — "set-up-a-new-project") rated P1

Persona 06 (Coach) and Persona 05 (Believer) both nominated a "Tutorial 1"
covering `bootstrap → connect → install-git-hooks → doctor` as P1 — "blocks the
start-from-nothing path."

I contest the P1 rating.

First, the honest comparison: what Spark is competing against is a developer who
already has Claude Code. That developer knows how to install a plugin. They do
not need a hand-held tutorial before they can run the first lifecycle skill — the
existing `how-to/install.md` and `build-your-first-project.md` together cover
enough ground for a motivated developer. A missing Tutorial 1 is a P2 gap, not
a P1 blocker. Nothing is broken without it; the adoption path is merely rougher
for the absolute beginner.

Second, the framing "blocks the start-from-nothing path" is a claim about user
behavior, not a ground-truth finding. The ground truth documents what is shipped;
it does not record whether users succeed or fail at setup. Escalating to P1 on
behavioral speculation is exactly the overclaim pattern the Skeptic watches for.

**Position:** Contest the P1. Re-grade to P2.

---

### B2. Contest: N10-2 (Awesome-list submissions) rated P1

Persona 10 (Discoverer) nominated awesome-list submissions as P1 — "high
community signal, compound discoverability." I contest the rating.

Awesome-list inclusion requires that the target repo is stable, licensed, and
documented. Spark currently has an unresolved license (N03-2, the P1 license
issue above) and a marketplace install that is unverified end-to-end. Submitting
to awesome-lists *before* those two issues are resolved is counterproductive:
curators will reject unlicensed software, or worse, accept it and send traffic to
a repo that fails the install step. The awesome-list submission is a *downstream*
task that becomes unblocked *after* P1 blockers are resolved.

Additionally, this is an operational task for the author, not a documentation or
code gap. Nominating it as P1 treats it as urgent work for the issue tracker when
it is actually a dependency-ordered prerequisite: fix license → fix install →
then submit. The issue itself is valid (submit to awesome-lists), but the priority
must reflect the dependency graph.

**Position:** Contest P1. Downgrade to P3. Gate it as "do after license + install
issues close." Add a dependency note.

---

### B3. Contest: N04-2 (CI workflow) priority vs. current architecture intent

Persona 04 (Evaluator) nominated CI as P2 with a strong case. I do not contest
the admission but I want to contest the framing that this is an "unintentional gap."

The positioning note is relevant here: one of Spark's genuine differentiators is
"guardrails are mechanical, not advisory." That enforcement lives in the hook
layer: `guard-bash.sh` (PreToolUse), `commit-msg`, and `pre-commit`. These are
the published enforcement model. CI on top would be belt-and-suspenders, but the
*current* enforcement story is coherent without CI — it is deliberate, not
overlooked.

I do not contest adding CI (it would be useful). But the issue copy must not
frame the CI absence as an "accidental gap" or a "contributor barrier" that
implies Spark's current quality story is broken. The honest framing is: "CI would
extend enforcement into the push pipeline; today enforcement lives in hooks and
local `spark doctor`; CI is a useful addition, not a missing piece of a broken
model." The Evaluator's nomination calls it "a gap — not a deliberate architectural
choice," but that reads as a claim unsupported by ground truth. Ground truth
documents the enforcement model without characterizing the CI absence as
unintentional.

**Position:** Admit as P2 but require the issue copy to state the honest framing:
CI extends the existing enforcement model; it does not fill a gap in a broken one.

I contest the admission entirely. This is a docit workflow completion task, not a

to the docit run. The Editor (12) owns this file's assembly — it is the output of
a process, not a gap to track in the repo's issue tracker. Filing a GitHub issue
for "create the docit run's output file" conflates the crew's internal workflow
with the repo's public issue backlog.

**Position:** Contest admission. Do not admit to the council issue list. The
Editor resolves this as part of the docit run deliverables.

### B5. Contest: N10-1 (GitHub topics) rated P1

Persona 10 (Discoverer) rated GitHub topics as P1 — "zero cost, immediate
discoverability lift." I contest only the P1 rating.

GitHub topics are configured in GitHub repository settings — they are not a file
change or a code change. They are a three-minute author action. P1 implies
blocking urgency; this is a trivial action that belongs in "do it now, five
minutes." Filing it as a P1 issue creates the impression that there is serious
blocking work to do when there is not. If the council admits this (it should,
the gap is real), rate it P3 — "quick win, do it, close it same day."

**Position:** Admit. Contest P1. Downgrade to P3.

## C. Counters (reframe or merge)

### C1. Counter: Merge `spark doctor` output-format cluster (N02-1, N00-4)

Persona 02 (Adopter) nominated "doctor output format unverified" as P1 with a
focus on newcomer trust. Persona 00 (Cartographer) nominated the same fact as N00-4
with a focus on docs quoting wrong strings.

Both are the same factual gap. There is one verified doctor output format:
`✓ <name>` per item and `Healthy — 0 errors, N warning(s)` at the end. The fix
is: (a) remove any doc or quickstart text that fabricates different output, and
(b) add the real output format to ground truth as a reference string. But this is
NOT a newcomer-trust blocker (N02-1's P1 claim) — a newcomer who runs `spark doctor`
sees the real output and forms trust from that; the docs saying "16 skills, 19
agents" is wrong but correctable. Over-rating this as P1 treats a docs inaccuracy
as a functional failure.

**Counter:** Merge into one issue. Rate P2 (docs accuracy, not a blocker). Issue
scope: (1) document the real doctor output format in ground truth / docs, (2)
strip any "16/19" summary claims from all affected drafts.

### C2. Counter: Skill-layout conflict (N05-5-canonical, N06-B, N07-1, N08-5) — admit but rate correctly

Four personas (05, 06, 07, 08) nominated the conflicting optional skill layout
specs as P1 or P2. The conflict is real and verified. I want to correct the
framing: this is a spec decision (pick one, update the other source) plus
documentation work. It is not a repo-correctness blocker — Spark's existing
skills all work; the conflict affects *new* skill authors, not existing users.

Calling it P1 on the grounds that it "blocks `write-a-skill` how-to and
agent-frontmatter reference" is correct but overcounts the urgency. Those docs
don't exist yet and aren't blocking anything that's currently working. The fix
is: make the decision, update the losing source, then write the how-to. That's
P2 work — important contributor-path improvement, not emergency.

**Counter:** Merge four nominations into one issue. Rate P2. Issue scope: decide
canonical layout, update source, create `docs/reference/skill-layout.md`.

### C3. Counter: Philosophy doc + enforcement-model + authorship-crews cluster

Personas 05 (Believer), 06 (Coach) each nominated:
- `docs/explanation/philosophy.md` shipping (N05-1, N06-G) — P1
- `docs/explanation/enforcement-model.md` (N05-2, N06-A) — P1
- `docs/explanation/authorship-crews.md` (N05-4, N06-E) — P2

My Skeptic read: the philosophy doc, enforcement-model, and authorship-crews docs
are all new documentation that the docit crew is recommending. They are valuable.
But calling the *absence of a brand-new doc* P1 ("blocking") is a category error.
P1 issues are things that are *wrong* — active overclaims, broken install paths,
falsified output. P1 is not "we recommend creating this doc."

None of these docs existed before this docit run. The repo functioned — and
users installed and used Spark — without them. Shipping a philosophy doc that
points to a non-existent enforcement-model doc is a Diátaxis mode issue (linking
problem), but it is not an emergency. It is a "do not ship philosophy without
its supporting links" constraint, which makes it a completion dependency, not a
P1 blocker for the whole repo.

**Counter:**
- `philosophy.md` shipping: admit as P2. The doc is ready; the constraint is
  "don't publish until enforcement-model.md exists or the link is removed."
- `enforcement-model.md`: admit as P2. Prerequisite for philosophy.md ship.
- `authorship-crews.md`: admit as P2 (as 06 rated it). Downgrade 05's P1 to P2.
These should ship together in one PR; create one issue that covers all three as a
linked work unit rather than three separate P1 issues.

### C4. Counter: N03-5 (no public comparison doc) — position this correctly

I nominated a "no public alternatives / comparison doc" as N03-5 at P2. No other
persona co-signed it. I want to argue it on its merits.

The full honest comparison — five alternatives, decision table, concessions,
"skip it when" line — is entirely in `.docit-notes/03-positioning.md`. It does
not exist in the public `docs/` tree. A skeptical developer landing after the
launch post has no pointer from the README to an honest comparison. The README
links to tutorials and how-tos but not to "should I even use this."

My claim: this is the most underrated issue in this entire council from a
positioning standpoint. A developer evaluating any tool wants "X vs. Y" first.
Spark does not have that page. The honest-hype contract is strongest here — the
comparison concedes where the alternatives are fine, which is exactly what builds
trust with a skeptical reader. Without a public counterpart to `03-positioning.md`,
that trust-building surface is locked in scratch notes.

I am pushing this from "no co-signs" to a co-sign from myself with added
justification: **this is P2 and should be admitted.** The target doc is
`docs/explanation/alternatives.md` (or folded into the philosophy doc's
"positioning" section — but it must be public).
