## STRONG CO-SIGNS (fight with full weight)

### License mismatch — hardest block I will defend

**Positions co-signed:** N00-1 (00), N01-2 (01), N03-2 (03), N05-3 (05), N09-3 (09),
N10-4 (10), NOM-11-1 (11).

This is the one issue where seven personas agree and I lead. Every co-nominator
is correct on substance; I will add precision for the debate.

**My case (strongest form):** The license mismatch is not a discoverability problem,
a visual problem, or a changelog problem — it is a **legal integrity problem**. A
developer who reads `plugin.json` and the README badge sees MIT; a developer who
reads the `LICENSE` file sees "License TBD." Those two signals cannot coexist in a
published repo. Any user who forks, redistributes, or incorporates Spark on the
strength of the MIT badge is acting on a false grant. This is the only issue in the
entire nomination set that creates real, external-party legal risk.

**On priority:** I am holding firm at **P1**. I reject any argument that this is
a P2 because "it doesn't block use." It blocks *redistribution*, it blocks
*institutional adoption*, and it undermines every honest-hype claim the project
makes — including the philosophy principle persona 05 champions.

**Proposed resolution (binary):** Either add the real MIT text to `LICENSE` or
remove the MIT badge and manifest entry and replace with "Proprietary — All Rights
Reserved" until a license is formally chosen. No middle ground; "License TBD" is
not an SPDX identifier.

**Counter to persona 10's framing (N10-4):** 10 calls this "P2 — medium urgency."
Contested. The Discoverer's framing ("blocks enterprise adoption") is correct but
understates the problem. This is P1 precisely *because* it blocks awesome-list
inclusion — and persona 10 is simultaneously nominating awesome-list submissions as
P1. You cannot nominate "submit to awesome lists" as P1 if the license issue is
only P2; the awesome-list submission requires a clean license, making the license
issue the upstream blocker for persona 10's own P1s.

### `codify` missing from CHANGELOG and README — must-fix before any launch

**Positions co-signed:** Evaluator's own N04-3; NOM-09-1 (09); NOM-11-2 (11).

**My case:** The changelog is the trust document for returning users. `codify`
shipped in commit `6ea36a7` (verified: `git log v0.2.0..HEAD`). Its absence from
`CHANGELOG.md` means the `[Unreleased]` section is an *inaccurate record* of what
HEAD contains. This is not just a discoverability gap — it is a falsified
changelog, which is exactly what the Keep-a-Changelog format is designed to
prevent. The `review` skill (`de7b9f9 feat: add review skill`) has the same problem
and should be in the same fix.

**Priority:** P2 for the changelog entry itself. I reject persona 09's P1 framing
("adoption blocker"). A missing changelog entry inconveniences; it does not legally
block. P1 is reserved for legal/trust failures (license, false claims). This is a
changelog maintenance gap — serious, must-fix before the v0.3.0 tag, but P2.

**Co-sign NOM-11-2's framing** that README also omits `codify` — the fix covers
both surfaces (CHANGELOG and README brief mention).

### CI gap — real contributor barrier, must not be soft-pedaled

**Position:** Evaluator's own N04-2.

**My case:** No `.github/workflows/` directory exists. This is a verified fact
(`04-trust.md` §"CI / automated testing"). The badge row analysis explicitly marks
CI as "NOT READY — omit until CI exists." No other persona nominated this — which
makes it uniquely mine to defend.

**Why this matters beyond cosmetics:** Contributors cannot know whether their
changes pass the project's own quality bar without running the CLI locally. The
CLAUDE.md says "run `spark doctor` before pushing" — that is an *advisory*
instruction, not mechanical enforcement. The whole philosophy of Spark is
mechanical enforcement. A project without CI is not following its own doctrine.

**Priority:** P2 (not P1 because no existing user breaks; this is a contributor
barrier and a maturity gap, not a legal/false-claim emergency). The fix is a
minimal GitHub Actions workflow: run `spark doctor` + `bash -n` on push/PR. Low
effort, high maturity signal.

**Contest:** I anticipate some personas will argue CI is "out of scope for docs."
It is not. The badge row is a docs surface; the trust note is a docs surface; the
maturity statement depends on what CI exists. A docs-only fix (drop the CI badge
claim) is the minimal acceptable resolution; adding actual CI is the preferred one.

## CONDITIONAL CO-SIGNS (with priority adjustments)

### Marketplace install caveat — co-sign but contest P1 rating from 01 and 03

**Positions partially co-signed:** N01-4 (01), N03-1 (03), N02-2 (02), NOM-11-4 (11).

**My position:** The marketplace install caveat is a real honest-hype gap (the
README presents an unverified install path without qualification), and it must be
fixed before launch. Ground truth is explicit: "v0.2 open item: validate install
end-to-end from a *published* marketplace (unchecked box)."

**Contest on priority:** Persona 01 rates this P1; personas 03 and 11 also call it
P1. I rate it **P2**. Here is why: P1 in my framework means legal or factual
failure that actively harms a user. An unqualified install command that *might* not
work is a bad user experience and an honest-hype violation, but it does not expose
users to legal risk or false factual claims about what the tool *does*. The fix is
a one-line caveat, not a rebuild. P2 is appropriate.

**Exception:** If the install command reliably fails in the real marketplace (i.e.,
the listing genuinely does not exist yet), then I would upgrade to P1 because it
becomes an active false claim. The ground truth says "unchecked box" — meaning
unverified, not confirmed broken. P2 unless confirmed broken.
